IoT Server 搭建手册

学习目标 工程目录 整体架构 核心组件 Web 后台 MQTT 服务 流媒体服务 CA 与证书 洪峰处理

从零搭建 IoT 服务器和云服务

本手册把工程目录编排、业务服务边界、双向认证、MQTT、流媒体、数据库和洪峰处理放在一个 HTML 中分章节说明。

学习目标

  • 理解 IoT 云服务工程的基本目录组织。
  • 理解 Web 后台、MQTT、流媒体、CA 证书系统各自负责什么。
  • 能够为 ESP32 设备建立基于证书的双向认证链路。
  • 能够为设备洪峰接入预留限流、缓存、队列和异步处理能力。

工程目录编排

本工程按业务服务拆分目录，每个目录可以独立开发、独立配置、独立容器化。

  • web-backend/: Web 后台、数据库访问、设备管理、证书元数据、审计日志。
  • mqtt-server/: MQTT Broker 配置、设备连接认证、Topic 权限、消息限流。
  • streaming-server/: Nginx 流媒体服务、拉流入口、流媒体限流和 mTLS 示例。
  • certs/: 本地开发证书说明和 CA 工具。
  • docs/: 单页学习手册。
  • docker-compose.yml: 本地联调编排文件。

管理流量、设备消息流量、媒体流量的性能模型和安全边界不同，所以目录和服务都需要拆开。

整体架构

平台目标是提供 IoT 设备后台服务，包括 Web 管理、数据库持久化、MQTT 消息、Nginx 流媒体拉流和证书认证。

服务边界

  • web-backend 管理设备、用户、证书、流地址、审计日志和数据库访问。
  • mqtt-server 管理设备长连接、Topic ACL、限流和遥测转发。
  • streaming-server 管理 Nginx 流媒体配置、拉流入口和流媒体限流。

推荐开源栈

  • PostgreSQL: 关系型元数据。
  • EMQX: MQTT Broker。
  • Nginx RTMP: 流媒体入门服务。
  • Redis: 热数据缓存和轻量限流状态。
  • Kafka 或 RabbitMQ: 遥测消息削峰缓冲。

核心组件是什么

这一节先解释工程中出现的组件各自是什么、解决什么问题，以及为什么放在 IoT 服务器里。

Docker Compose

docker-compose.yml 是本地联调编排文件。它不是把所有服务塞进一个容器，而是用一个文件同时管理多个独立容器，例如数据库、MQTT Broker 和流媒体服务器。

PostgreSQL

PostgreSQL 是关系型数据库，用来保存设备、用户、证书、流地址、审计日志等结构化数据。它适合作为后台管理系统的核心数据存储。

Web Backend

Web 后台是你自己开发的业务服务。它负责提供管理 API、读写 PostgreSQL、维护设备状态、管理证书状态，并把设备数据变成后台可以查询和操作的业务数据。

EMQX

EMQX 是 MQTT Broker。ESP32 这类设备通常不适合频繁发 HTTP 请求，MQTT 更适合长连接、低带宽、弱网络环境。EMQX 负责接收设备连接、校验证书、管理 Topic、转发消息和限制异常流量。

MQTT

MQTT 是一种发布/订阅消息协议。设备把遥测数据发布到 Topic，云端服务订阅这些 Topic；云端也可以向设备命令 Topic 发布控制消息。

Nginx RTMP

Nginx RTMP 是基于 Nginx 的流媒体模块，用来学习和搭建推流、拉流能力。设备或边缘网关可以推流到 RTMP 服务，用户或后台服务再从服务器拉流。

CA

CA 是证书签发机构。你自己生成一个本地 CA 后，可以用它签发服务器证书和每台 ESP32 的设备证书。服务器和设备都信任同一个 CA，才能建立双向认证。

mTLS

mTLS 是双向 TLS。普通 TLS 只要求设备验证服务器身份；mTLS 还要求服务器验证设备身份。这样 ESP32 访问 MQTT 或其他设备入口时，必须携带自己的客户端证书。

Redis

Redis 是内存型缓存。它适合保存热点设备状态、短期限流计数、幂等键和临时会话信息，能减少数据库压力。

Kafka 或 RabbitMQ

Kafka 和 RabbitMQ 都是消息队列。设备洪峰上报时，队列可以先接住大量消息，再让后台消费者按数据库能承受的速度慢慢处理。

Web 后台如何搭建

Web 后台是 IoT 云服务的大脑，负责管理平台数据和提供管理接口。

核心职责

  • 管理设备档案、设备证书和证书状态。
  • 管理用户、角色和后台权限。
  • 记录设备事件和审计日志。
  • 管理流媒体地址和设备配置。

数据库起步表

  • devices: 设备 ID、名称、状态、证书指纹、创建时间。
  • device_certificates: 证书序列号、设备 ID、有效期、吊销状态。
  • device_events: 设备事件、上报时间、处理状态。
  • streams: 设备流地址、协议、状态。
  • audit_logs: 管理员操作日志。

后台不应该直接相信请求体里的 deviceId，设备身份应来自 mTLS 证书解析结果。

MQTT 服务如何搭建

MQTT 服务器负责设备长连接、消息上报和指令下发。当前建议使用 EMQX。

设备接入流程

  1. ESP32 内置 ca.crt、设备证书和设备私钥。
  2. ESP32 连接 mqtts://server:8883。
  3. EMQX 使用 CA 校验 ESP32 客户端证书。
  4. ESP32 使用 CA 校验服务器证书。
  5. EMQX 根据证书身份绑定设备 ID，并按设备权限限制 Topic。

Topic 设计

  • devices/{deviceId}/telemetry: 设备遥测上报。
  • devices/{deviceId}/event: 设备事件上报。
  • devices/{deviceId}/command: 云端指令下发。
  • devices/{deviceId}/status: 设备在线状态。

流媒体服务如何搭建

流媒体服务器负责设备视频流的接入和拉流。当前建议先基于 Nginx RTMP 学习搭建。

  1. 设备或边缘网关推流到 Nginx RTMP。
  2. Nginx 暴露拉流或统计入口。
  3. Web 后台保存设备和流地址的绑定关系。
  4. 私有流通过网关鉴权、mTLS 或短期签名 URL 保护。
  5. 高并发拉流时扩容流媒体节点或引入 CDN。

CA 与证书如何搭建

CA 用于签发服务器证书和 ESP32 设备证书，是双向认证的基础。

需要生成什么

  • CA 证书和 CA 私钥。
  • 服务器证书和服务器私钥。
  • 每台 ESP32 独立的设备证书和设备私钥。

本地命令

python -m certs.ca.ca_tool create-ca
python -m certs.ca.ca_tool sign-server --common-name localhost --dns-name localhost --ip-address 127.0.0.1
python -m certs.ca.ca_tool sign-device --device-id device001
python -m certs.ca.ca_tool install-server

生成产物统一放在 certs/ca/output/，例如 output/ca/ca.crt、output/issued/server.crt 和 output/issued/device001.crt。

CA 生成产物作用

文件 作用 使用位置 安全要求
certs/ca/output/ca/ca.crt CA 公钥证书，用来证明“哪些服务器证书、设备证书是这个 CA 签发的”。 复制给 EMQX、Nginx、ESP32。服务器用它验证设备证书，ESP32 用它验证服务器证书。 可以分发，不是私密文件，但要保证来源可信，避免设备信任错误 CA。
certs/ca/output/ca/private/ca.key CA 私钥，用来签发服务器证书和设备证书。 只在签发证书时由 ca_tool.py 使用。 必须严格保密。泄露后别人可以伪造服务器或设备证书，应废弃整个 CA 并重新签发。
certs/ca/output/issued/server.crt 服务器证书，证明 EMQX 或 Nginx 服务端身份。 安装到服务器侧，例如 EMQX 的 TLS 监听器或 Nginx HTTPS/mTLS 入口。 可以随服务部署，不是私钥；需要和对应 server.key 配对使用。
certs/ca/output/private/server.key 服务器私钥，服务器用它完成 TLS 握手。 只放在服务器侧，例如 EMQX 或 Nginx 容器挂载目录。 必须保密。泄露后攻击者可能冒充你的服务器。
certs/ca/output/issued/device001.crt ESP32 设备证书，证明某台设备的身份。 烧录或写入对应 ESP32，用于连接 MQTT mTLS。 可以放入设备，但每台设备应唯一，后台用证书 CN、SAN 或指纹绑定设备 ID。
certs/ca/output/private/device001.key ESP32 设备私钥，设备用它证明自己持有对应证书。 只写入对应 ESP32，配合 device001.crt 使用。 必须保密。泄露后应禁用该设备证书并重新签发。

每台设备独立证书可以做到单独禁用、单独追踪，避免一台设备泄露后影响全部设备。

流量洪峰处理

流量洪峰不能只靠单个服务硬扛，应使用分层成熟方案。

  1. 边缘保护：Nginx limit_req、limit_conn、请求体限制和超时。
  2. Broker 保护：EMQX 连接限制、发布速率限制、Topic ACL 和集群模式。
  3. 消息缓冲：Kafka 或 RabbitMQ 承接 MQTT 遥测流量。
  4. 缓存和背压：Redis 缓存设备元数据、幂等键和短期限流状态。
  5. 数据库保护：批量写入、异步消费、索引和连接池限制。
